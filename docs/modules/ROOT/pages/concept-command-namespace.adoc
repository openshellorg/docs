= Command namespace and context requests
:description: Proposed. Replace PATH lookup, the current-folder prompt and environment activation with a hierarchical command namespace, declared input signatures, and named isolation levels.
:page-audience: Shell designers, CLI authors, package-manager and version-manager authors
:page-usage-context: When deciding how a shell finds commands, how a command learns the current folder, or how a session switches tool versions
:page-orig-author: Grok Bot on behalf of Ryan Johnson
:page-orig-author-github: AMDphreak
:page-last-author: Grok Bot on behalf of Ryan Johnson
:page-last-author-github: AMDphreak

CAUTION: *Concept, proposed.* Nothing here is part of The Standard yet. Rule ids (`NS-n`) are provisional and may change before any part is adopted.

Today a shell gives commands their context in three implicit ways: it finds them by searching the folders on `PATH`, it hands every process the current folder whether or not it needs one, and it "activates" environments by editing variables in the session.
This page proposes replacing all three with explicit models: a hierarchical *command namespace*, *input signatures* that say which context a command will request, and named *isolation levels* for anything that changes the namespace for a while.

The key words MUST, SHOULD and MAY follow https://www.rfc-editor.org/info/bcp14[BCP 14].

== Why change

* *PATH is a flat list searched in order.* Every command competes for one name; the winner is decided by folder order that installers edit and users cannot see; nothing records who put a name there or which version it is.
* *The current folder is ambient.* It is printed before the prompt as if it were part of every command, and every process inherits it. The user cannot tell before pressing Enter whether a command will act on it.
* *Activation is a hidden edit.* A Python venv is a persistent folder; `activate` only edits `PATH`, `VIRTUAL_ENV` and the prompt for one session. The edit is invisible except for a prompt prefix, and the word "environment" hides what actually changed. See link:https://devcentr.org/blog/2026-10-26-virtual-environments-are-neither-virtual-nor-temporary[Virtual environments are neither virtual nor temporary].

Programming languages solved the first problem long ago with modules and qualified names. The context a person works in should come from what they want to do, not from which folder they are in.

== Command namespace

NS-1:: A conforming shell MUST resolve the first word of a command through a hierarchical command namespace, not by searching folders. Nodes are slash-separated paths of lowercase words grouped by task, for example `install`, `install/npm`, `vcs/status`.

NS-2:: A tool MUST enter the namespace by a *registration manifest* that names every node it claims, its package, version and publisher. The shell host MUST record each registration (who, what, when). Manifests are written in JSON5 and validated by JSON Schema after parsing (see https://github.com/openshellorg/command-namespace[command-namespace]).

NS-3:: Two manifests claiming the same node MUST be reported as a conflict. The shell MUST NOT let the most recent installer win silently.

NS-4:: An unknown first word MUST be a usage error with did-you-mean across the namespace, as xref:standard-cli-dispatch.adoc[CLI Dispatch] CD-1 requires of a single tool.

NS-5:: Running a file by path MUST stay possible, but only explicitly (a path-shaped token or a `run` command). A shell MAY import `PATH` as a read-only `legacy` subtree during migration and MUST mark commands resolved that way.

NS-6:: A node MUST declare its CLI style (strict by default, per xref:standard-cli-styles.adoc[CLI Styles] CS-1 and CS-2). A resolver-style front door such as `install` is a node whose children are providers registered by each package manager. The command is literally `install`, to keep the interface seamless; on Unix the existing `install(1)` file copier is registered at `legacy/install`, and install(1)-style arguments are handed through to it so build scripts keep working (passthrough PROVISIONAL).

NS-7:: A tool SHOULD publish its own token table (subcommands, contextual flags, free flags) in its manifest and SHOULD use the same table in its own parser. This lets inspection tools list commands, flags, conflicts and installed packages across every manager without running any command or its help. Free flags are non-contextual: they mean the same in every command, use the `+` sigil, and their order doesn't matter (`+yes +verbose`); repeating the sigil steps through levels. Contextual flags use `-`: their meaning depends on the verb and their position matters (`install -npm <pkgname>`), and their spelling follows NS-15 (<<option-syntax>>). The inspection tool is https://github.com/openshellorg/name[`name`] (`name which`, `name conflicts`).

NS-8:: When a version manager controls a node, the manifest for each version SHOULD mark which commands and flags were added, removed or changed since the previous release. This is a visual cue and learning aid, not a full diff.

== Context requests

NS-9:: A command node SHOULD publish an *input signature* declaring which ambient context it will request: current folder (none, read, write, and under which flags), named environment variables, identity, network and stdin.

NS-10:: A shell MUST give a command the current folder only when its signature requests it (native protocol), and SHOULD show, before the command runs, whether the folder will be used. A command with no signature MUST be shown as "may use current folder".

NS-11:: The current folder SHOULD be displayed as an input at the end of the command line, truncated to at most half the screen width, with a setting to keep the leaf folder at the right or left edge of its slot.

NS-12:: The command composition area SHOULD keep a fixed height of two to three lines (context, input, transient status) so that status shown while typing does not move the input line. This extends the two-line layout in xref:shell-architecture::prompt-spatial-layout.adoc[Prompt spatial layout] and the multi-line paste preview in xref:shell-architecture::shell-display-layers.adoc[Shell display layers].

== Isolation levels

NS-13:: Anything that changes the namespace or the process's view of the system for a while SHOULD be described by three properties: *level* (overlay, fence, partition, guest), *lifetime* (run, session, kept), and *scope* (process, session, folder, user, machine). Definitions: link:https://docs.devcentr.org/general-knowledge/reference/shells/isolation-levels.html[Isolation levels] (Dev-Centr glossary).

NS-14:: An overlay (venv activation, a version switch, a project pin) SHOULD be implemented as a layer on top of the command namespace, with precedence machine < user < folder < session, and MUST be shown in the composition area with its full term, for example "kept overlay: .venv, attached to this session".

[#option-syntax]
== Option syntax (NS-15)

NS-15:: A conforming tool's own options MUST use a single dash (`-`), read by these rules. `-` options are the contextual flags of NS-7: their meaning depends on the verb and their order matters (`install -npm <pkgname>`). The rules apply to any argument that starts with `-` and is not exactly `-`; the `+` free (non-contextual) flags of NS-7 are not affected.
+
. `-word` is a *long option*. A word is two or more characters, and hyphenated words are allowed: `-version`, `-dry-run`, `-strict-dispatch`.
. A *short alias* is a single letter: `-v`. A short alias and a long option MAY name the same option (`-v` and `-version`).
. There is *no implicit bundling*. `-xvz` MUST be read as the long option named `xvz`, never as `-x -v -z`.
. *Explicit grouping* is single letters joined by hyphens: `-x-v-z` means the switches `x`, `v` and `z`. Every part of a group MUST be one letter.
. A long option name MUST NOT start with a single letter followed by a hyphen (`-d-lang`, `-f-stop`, `-f-number`); spell it `-dlang`, `-fstop`, `-fnumber`. A token that starts like a group and continues with a longer word (`-d-lang`, `-x-dry-run`) MUST be a usage error (xref:standard-cli-dispatch.adoc[CD-8]: stderr, exit `2`).
. A lone `-` is an operand, not an option (stdin or stdout, as in `-f -`), and MUST stay legal.
+
`--long` is a deprecated legacy alias, scheduled for deletion in the next major revision of the standard; frameworks MUST warn about it at build time and at run time (<<legacy-double-dash>>). Repeated dashes (`--x`, `---x`) are reserved for a future meaning, which is OPEN (<<reserved-repeated-dash>>). Documentation and examples MUST use the single-dash form.

=== Grammar

Split the text after the leading `-` on `-` into parts. The first part decides:

[source,text]
----
token   = "-"                              ; operand (stdin/stdout), NS-15 item 6
        | "-" letter                       ; short alias            -v
        | "-" letter 1*("-" letter)        ; explicit group         -x-v-z
        | "-" word *("-" part)             ; long option            -version, -dry-run, -xvz
        | "--" ...                         ; deprecated legacy alias of "-"; repeated "-" reserved (see below)
letter  = %x61-7A / DIGIT                  ; one character
word    = 2*( %x61-7A / DIGIT )            ; two or more characters
part    = 1*( %x61-7A / DIGIT )
; anything else whose first part is one letter
; (a letter, then a part of two or more characters) is a usage error
----

Later one-letter parts inside a long name (`-ipv-4`) are legal; only the *first* part decides between group and long name.

=== Why

* *Bundling reads as a word.* tar's `-xvz` packs three switches into something that looks like a command named `xvz` ("what is xvz, are we x-vizzing it?"). Under NS-15 a token always means what it spells.
* *Grouping needs a visible separator that survives every shell.* A colon (`-:xvz`) never reads as grouping; quotes (`-"xvz"`) are stripped by the shell; `;` ends a command; parentheses need quoting in bash and PowerShell. A hyphen between single letters is plain, typeable and unquoted everywhere.
* *Letter-hyphen names are ambiguous.* Cabal's `-f-foo` means "disable flag foo", which is exactly the `-f -foo` versus `-f-foo` ambiguity this rule removes; GHC avoids it with `-fno-foo` and `-XNoFoo`. Banning a leading letter-hyphen keeps every group unambiguous.

[#legacy-double-dash]
=== `--long` is a deprecated legacy alias (decided)

*Status: Decided.* `--long` (GNU style) is a *deprecated legacy alias* of `-long`, scheduled for deletion in the next major revision of the standard. Repeated dashes (`--`, `---`) are reserved for a future meaning (<<reserved-repeated-dash>>), so the alias cannot stay.

* Until that revision a tool MAY accept `--long` as an alias of `-long`. Documentation, help and examples MUST NOT show it.
* A conforming CLI framework or library (for example prohelp, or wrappers around arsd.cli) MUST warn at compile or build time when a tool declares a `--` spelling, naming the single-dash replacement.
* A conforming framework or library, and any tool that accepts the alias, MUST warn at run time when a user types a `--` form: on stderr, in the CD-13 format, naming the single-dash replacement. For example:
+
[source,text]
----
warning: '--help' is deprecated and scheduled for deletion in the next major revision of the standard
  use: <tool> -help
----
* The bare end-of-options marker `--` (a token that is exactly `--`) is a separate, undecided question; see <<reserved-repeated-dash>> for how it relates to the reservation.

[#reserved-repeated-dash]
=== Repeated `-` is reserved (OPEN)

*Status: OPEN, for Ryan to decide.* What `--x` and `---x` will mean is not decided; until then they are reserved, and new tools MUST NOT give them a meaning of their own.

`+` and its repetitions belong to free, non-contextual flags (NS-7). `-` belongs to contextual options, whose meaning depends on the verb and whose position matters (`install -npm <pkgname>`). So whatever repeated `-` comes to mean applies to contextual options only, and does not overlap with `+` levels. Two candidates are open, plus leaving it reserved.

==== Candidate A: intensity

More dashes ask for more of the same contextual option. The user infers what "more" means for a given option (Ryan); the tool's help says it. Scope, config reach and the danger-confirmation gate are not separate meanings. They are what intensity happens to mean for particular options:

* *Danger gate* (Ryan: "good idea"). For a destructive option, more intensity means a stronger action, and the strongest forms ask for confirmation:
+
[source,text]
----
$ install -clean ripgrep     # remove ripgrep's cached downloads
$ install --clean ripgrep    # also remove its installed files; asks for confirmation first
$ install ---clean ripgrep   # also remove its config and data; asks, and requires the package name to be typed again
----
* *Scope.* For an option like `-verbose`, more intensity means it travels further down the command line:
+
[source,text]
----
$ vcs -verbose status        # verbose applies to vcs itself (its dispatch and setup), not to status
$ vcs --verbose status       # also passed on to the status subcommand and anything it runs
$ vcs ---verbose status      # set for the rest of the session (every later command)
----
* *Config reach.* For a preference, more intensity means it is saved further out:
+
[source,text]
----
$ install -prefer-npm prettier     # this run only
$ install --prefer-npm prettier    # also saved in the project config (./.oso/install.json5)
$ install ---prefer-npm prettier   # also saved in the user config (~/.config/oso/install.json5)
----
(Paths are illustrative.)

[#hierarchy-candidate]
==== Candidate B: hierarchy depth (Ryan's favoured direction, not decided)

The number of dashes is the option's depth under the nearest preceding option with one dash fewer:

[source,text]
----
$ encode -codec x264 --crf 23 --preset slow -output out.mkv
----

`--crf` and `--preset` are children of the preceding `-codec`. Going back to a single dash (`-output`) is the visible break out of that context: `-output` is a sibling of `-codec`, not a codec setting.

*Why.* Ordering alone cannot show whether an option is a sibling or a child. A parser could work it out from a hidden schema ("`-crf` only belongs to codecs, so attach it to `-codec`"), but then the user has to know that schema to read the line, which breaks their mental model of what they typed. Dash depth puts the tree on the command line. It matches prohelp's hierarchical help: `help -codec` lists the children of `-codec`, and the same children are what may follow it with `--`.

*Intensity moves to a suffix.* Under this candidate, repeated dashes are taken by depth, so intensity is written as a suffix on the option word. The suffix is `!` (decided by Ryan, see <<intensity-suffix>>):

[source,text]
----
$ vcs push -force!       # stronger push; may ask for confirmation
$ install -clean!! ripgrep
----

*Open sub-questions:*

* *What `---` means.* Presumably a grandchild (a child of the nearest preceding `--` option). Not decided.
* *A child with no parent.* `encode --crf 23` with no `-codec` before it. Likely a usage error (CD-8: stderr, exit `2`, "`--crf` needs a parent option such as `-codec`"). Not decided.
* *Interaction with the `--long` legacy alias* (<<legacy-double-dash>>). During the transition, `--word` straight after a parent option could be a child or the deprecated spelling of `-word`. Proposed resolution, OPEN: a tool may use child options only if it declares no `--` legacy spellings at all; a tool that still has legacy spellings reads `--word` as the legacy alias only where no parent context is open (as the first option, or right after a parent's operands end in a way the tool's schema makes unambiguous) and otherwise as a child. The simpler rule (no children while any legacy spelling exists) is recommended, because it needs no schema to read.

==== Leave it reserved

Repeated `-` keeps no meaning.

[#intensity-suffix]
==== Intensity suffix `!` and the fallback `~`

*Decided (Ryan):* `!` is the canonical intensity suffix (`-force!`, `-clean!!`). Ryan: shells that break `!` "need to get on my level, not I on theirs". The hierarchy candidate as a whole stays OPEN; the suffix character does not.

* *Non-conforming shells.* Interactive bash and interactive zsh expand `!` (history expansion) by default, so `-clean!!` arrives as `-clean` followed by the previous command line. These shells are NON-CONFORMING for OSO unless history expansion is turned off. The fix, in the rc file:
+
[source,bash]
----
# ~/.bashrc
set +H                 # same as: set +o histexpand
----
+
[source,zsh]
----
# ~/.zshrc
unsetopt BANG_HIST
----
+
A tool cannot change its parent shell, so this is user setup. An OSO installer or setup script MAY add these lines.
* *Fallback suffix (PROVISIONAL, chosen by test, for Ryan to confirm): `~`.* Conforming tools MUST accept `~` with exactly the same meaning as `!` (`-force~`, `-clean~~`), only as a stand-in for `!` in shells that mangle it. `~` was the only tested character that is not already a sigil (`+` is taken by free flags) and reached the program unchanged in every shell tested, including zsh with `extendedglob` (a trailing `~` is not a pattern) and bash/zsh tilde expansion (which only applies at the start of a word).
* *Which spelling docs and help teach (Decided, Ryan).* "The docs/instructions should/will teach different syntax for those shells until they redress their bad choice." Documentation, instructions and tool help teach `~` for interactive bash and zsh (and any other shell that is not OSO certified for `!`) until those shells fix it, and `!` everywhere else. The canonical spelling is still `!`. Turning history expansion off (`set +H`, `unsetopt BANG_HIST`, above) is how a bash or zsh user becomes conforming and can type `!`. Where help adapts to the shell, it uses the same detection as the notices: bash, zsh and undetectable shells are shown `~`.
* *No guard against mangled `!` (Decided, Ryan).* "If someone attempts to use the wrong syntax in zsh, they should just see bad output." Tools do not try to detect arguments that history expansion has mangled (`-cleanpython3 ...`), and help carries no extra warning about it: the user gets whatever the mangled arguments produce, usually an unknown-option usage error (CD-8). A shell-side companion (a plugin that rewrites `!` before the shell expands it) is not planned.
* *Fallback notice (MUST).* Ryan: when a fallback is used, it must be "abundantly obvious that the incompatible shells are incompatible and not oso certified". Whenever a conforming tool receives an option with the `~` fallback suffix, it MUST print a prominent notice on stderr, on every use. The notice does not change stdout or the exit code, and `-quiet` MUST NOT silence it. It MUST be visibly highlighted: a coloured `notice:` label when stderr is a terminal, plain text otherwise (CH-19). It MUST:
** say that the fallback was used because the current shell expands `!` and is not OSO certified;
** name the shell when it can be detected. `$BASH_VERSION` and `$ZSH_VERSION` are shell variables that a child process does not see, so detect it from the parent process instead (`/proc/$PPID/exe` or `ps -p $PPID -o comm=` on Unix, the parent process image on Windows), falling back to `$SHELL` (the login shell, which may not be the one running) and saying "your shell" when nothing is reliable;
** link the OSO certification page (https://docs.opensh.org/open-shell-org/certification-about/);
** ask the user to request OSO certification from the shell's maintainers, with a link to where that request goes when one is known;
** give the fix: `set +H` in `~/.bashrc`, or `unsetopt BANG_HIST` in `~/.zshrc`.
+
Example (stderr; `notice:` coloured on a terminal):
+
[source,text]
----
notice: '-clean~~' used the fallback suffix '~' for '!'.
  Your shell (zsh, from the parent process) expands '!' and is not OSO certified:
  https://docs.opensh.org/open-shell-org/certification-about/
  Please ask the zsh maintainers to seek OSO certification: https://www.zsh.org/mla/
  Fix it now: add 'unsetopt BANG_HIST' to ~/.zshrc, then type -clean!!
----
+
*Silencing: Decided (Ryan).* "I'd rather it complain every time to drive the point home." The notice MUST be printed on every invocation that uses the fallback suffix. There is no mute of any kind: no environment variable, no config setting, no once-per-session mode, and `-quiet` does not suppress it.
* *Fallback used where `!` works (MUST).* Ryan: "If someone uses a compat syntax in a shell that supports !, we should complain there too". When a conforming tool receives the `~` fallback and the detected shell passes `!` through unchanged, it MUST print a different notice on stderr, on every use. There is no mute, `-quiet` does not suppress it, and stdout and the exit code are unchanged. The notice says the fallback is only for shells that are not OSO certified, that this shell supports `!`, and gives the canonical spelling. If the shell cannot be detected, the tool prints the not-certified notice instead.
+
Example (stderr; `notice:` coloured on a terminal):
+
[source,text]
----
notice: '-clean~~' used the fallback suffix '~', which is only for shells that are not OSO certified.
  Your shell (fish, from the parent process) supports '!'.
  use: install -clean!! ripgrep
----
* *What the library can detect (PROVISIONAL).* The CLI framework library decides which notice to print, on its own, with no help from the shell:
** *Shell identity: detectable.* The parent process is the shell that ran the tool: `/proc/$PPID/exe` or `ps -p $PPID -o comm=` on Unix, the parent process image on Windows. When the parent is a launcher (`env`, `sudo`, `make`) rather than a shell, walk up the process tree; `$SHELL` names only the login shell and is a last resort.
** *History-expansion state: not detectable.* A child process cannot see whether the parent bash or zsh has history expansion on, or whether it is interactive. `$BASH_VERSION`, `$ZSH_VERSION`, `set -o` and `setopt` state are not exported, and stdin being a terminal is only a heuristic (an interactive shell running a script still gives the script a terminal).
** *So:* fish, PowerShell 7, Windows PowerShell 5.1 and cmd (delayed expansion off is the default; the library cannot see `/v:on` either) get the "supports `!`" notice. bash and zsh always get the not-certified notice, even when history expansion is in fact off or the run is non-interactive, because the library cannot tell. Unknown shells get the not-certified notice.
** *OPEN (Ryan undecided): an environment hint.* The user's rc file could export a variable such as `OSO_SHELL_BANG=literal` (next to `set +H` / `unsetopt BANG_HIST`) or `OSO_SHELL_BANG=expands`, and the library would trust it for bash and zsh. Not adopted; without it, bash and zsh default to the not-certified notice.

.Unquoted suffix safety (tested 2026-10-26; bash 5.2, zsh, fish, PowerShell 7.4.6 on Linux; Windows PowerShell 5.1 and cmd.exe on Windows 11)
[cols="1,1,1,1,1,1,1,1,1"]
|===
|Arg |bash -c |bash -i |zsh -c |zsh -i |fish |pwsh 7 |PS 5.1 |cmd

|`-force!` |ok |ok^1^ |ok |ok^1^ |ok |ok |ok |ok^2^
|`-clean!!` |ok |*expanded* |ok |*expanded* |ok |ok |ok |ok^2^
|`-x~` |ok |ok |ok |ok |ok |ok |ok |ok
|`-x+` / `-x++` |ok |ok |ok |ok |ok |ok |ok |ok
|`-x^` / `-x^^` |ok |ok |ok^3^ |ok^3^ |ok |ok |ok |*stripped*
|`-x*` |glob^4^ |glob^4^ |*error* |*error* |*error* |ok |ok |ok
|`-x%` |ok |ok |ok |ok |ok |ok |ok |ok^5^
|`-x=` |ok |ok |ok |ok |ok |ok |ok |ok^6^
|`-x@` |ok |ok |ok |ok |ok |ok |ok |ok
|`-x.` |ok |ok |ok |ok |ok |*split* |*split* |ok
|`-x:` |ok |ok |ok |ok |ok |*error* |*error* |ok
|`-x#` |ok |ok |ok^7^ |ok^7^ |ok |ok |ok |ok
|===

ok = the program received the exact literal argument. *expanded*: `-clean!!` became `-cleanpython3 a.py -force!` (the previous line). *stripped*: cmd removed `^` (its escape character), the program got `-x`. *error*: zsh and fish "no matches found" for `-x*`; PowerShell "Parameter -x: requires an argument". *split*: PowerShell passed `-x` and `.` as two arguments.

. A lone trailing `!` survives, but `!` followed by text (`-force!x`) gives "event not found".
. With delayed expansion on, `!` is stripped.
. With `setopt extendedglob`, `^` is a glob operator: "no matches found".
. Passed literally only when no file matches `-x*`; with a file `-xA` present, bash passed `-xA`.
. Literal at the prompt and through `%*`, but `%` is special inside batch files.
. Reached the program through `%*`; cmd treats `=` as an argument separator for `%1`-style access.
. With `setopt extendedglob`, `x#` is a glob ("zero or more x"): "no matches found".

PowerShell's `@` (splatting) and `#` (comment) are special only at the start of a word, and `--%` (stop parsing) only as a whole word, so none of them affected a trailing suffix. Test harness: an argv-echo program (`python -c "import sys;print(sys.argv[1:])"`), invoked through each shell, with interactive bash and zsh fed the commands on stdin so history expansion was on.


*Bare `--`:* whether the token `--` (exactly two dashes, nothing after) stays the end-of-options marker is a separate question. It does not conflict with reserving `--x` and `---x`, because it has no name after the dashes. It could conflict with a candidate that gives a bare repeated dash a meaning of its own (for example a bare `---` for "session scope from here on"); if one of those is chosen, the end-of-options marker has to be decided at the same time.

== What already exists, and what is new

* *Plan 9* has no `PATH`; `/bin` is a union of bound folders in a per-process namespace. This page keeps the per-session layering but makes the tree one of tasks with metadata, not of files.
* *PowerShell* finds cmdlets by verb-noun through modules and `Get-Command`, and exposes stores as drives through providers. Module lookup still walks a path list (`PSModulePath`), and native executables still use `PATH`.
* *Windows App Paths* is a registry of command names to executables used by `ShellExecute`, not by consoles. It is flat and has no metadata.
* *Nushell* gives built-in commands declared signatures; external commands are still found on `PATH`.
* *git, cargo and kubectl plugins* fake a hierarchy with file names (`git-foo` becomes `git foo`).
* *Nix, Homebrew, Debian alternatives, asdf and mise* control which binary a name points to, by profiles, links or shims; they still publish into one flat `PATH`.

New here: externals register into one task-shaped tree with owners, versions and signatures; the current folder becomes a declared input; and temporary changes are named by level, lifetime and scope.
