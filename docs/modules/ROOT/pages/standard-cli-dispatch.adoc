= CLI Dispatch
:description: How a CLI maps the words it is given to actions: unknown commands are errors, bare words never run anything implicitly, and unexpected input is rejected.
:page-audience: CLI authors, tool maintainers, wrapper and drop-in replacement authors, agent authors
:page-usage-context: When designing how a command decides what to do with its arguments, what a bare invocation does, and how to retire implicit behaviour in an existing tool
:page-orig-author: Grok Bot on behalf of Ryan Johnson
:page-orig-author-github: AMDphreak
:page-last-author: Grok Bot on behalf of Ryan Johnson
:page-last-author-github: AMDphreak

A command line is an instruction.
A conforming tool does exactly what it was told, refuses what it does not understand, and never guesses its way into fetching, building or running something the user did not name.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in https://www.rfc-editor.org/info/bcp14[BCP 14] (RFC 2119, RFC 8174) when, and only when, they appear in all capitals.

In this page, a *conforming tool* is a CLI that claims conformance with this standard, and a *command token* is the word in the position where the tool expects a command or subcommand name.
Requirement ids (`CD-n`) are stable so tools, reviews and certification can cite them.
Where and how errors are printed is governed by xref:standard-cli-output.adoc[CLI Output]; this page governs which input produces an error at all.

NOTE: This page is about how a single tool dispatches its own arguments.
It is unrelated to Entrypoint Dispatch in `shell-architecture`, which covers how a shell refuses or re-executes entrypoints.

== Unknown commands

CD-1:: An unknown command token MUST be an error. A conforming tool MUST:
. print `unknown command <X>`, naming the token it received;
. offer a did-you-mean suggestion when a known command is close (for example by edit distance or prefix);
. list the valid commands, or point to the exact help command that lists them;
. write all of this to stderr (xref:standard-cli-output.adoc[CO-20]);
. exit with the usage error code `2` (xref:standard-cli-output.adoc[CO-18]).

CD-2:: A tool MUST NOT perform any action (network access, file writes, builds, process launches) before it has determined that the command token is known.

== No implicit catch-all

CD-3:: A bare word MUST NOT be silently treated as a package, file or target to fetch, build or run.
Running a package or target MUST require an explicit command (for example `run <pkg>`).
A command token that does not match a known command is an unknown command (CD-1), never a fallback target.

CD-4:: Aliases and abbreviations of commands MAY exist only when they are documented and fixed.
A tool MUST NOT resolve a token by searching packages, files, plugins or the network for something that happens to share its name.

== Bare invocation

CD-5:: In the strict style (see <<cli-styles>>), a bare invocation (the tool name with no command) SHOULD print help (or a short usage summary pointing to help) and perform no action.

CD-6:: If a tool does have a default action for a bare invocation, that default MUST be documented in its help and reference documentation, and every bare run MUST state which action it ran (for example `no command given; running default: build`).
The default action MUST NOT be a catch-all that interprets later words as targets (CD-3 still applies).

== Unexpected input

CD-7:: Unexpected input MUST be rejected, including by tools that take no arguments.
A tool or GUI launcher that accepts no positional arguments or flags MUST exit with an error (usage code `2`, message on stderr) when it receives any, instead of silently ignoring them, so users know there is no hidden surface.

CD-8:: Unknown flags, surplus positional arguments, and missing required arguments MUST be errors under the same rules as CD-1: name the offending input, point to help, write to stderr, exit `2`.

== Wrappers and drop-in replacements

CD-9:: A wrapper or drop-in replacement MUST forward only the commands it knows the underlying tool implements.

CD-10:: For any other command, a wrapper or drop-in replacement MUST NOT forward, guess or fall back.
It MUST fail with an error that says this tool does not implement the command and names the tool that does (for example `redub does not implement 'search'; use dub search`), on stderr, with exit code `2`.

== Migration for tools with implicit behaviour

CD-11:: An existing tool that has implicit behaviour (a catch-all, a silent default, ignored arguments) MUST, in its current major version:
. warn on *every* implicit use, on stderr, with the explicit replacement spelled out in full (for example `use: dub run foo`);
. offer an opt-in strict mode, by flag, config setting and environment variable, that turns every implicit use into the CD-1 / CD-7 error.

CD-12:: In the next major version, strict errors MUST become the default.
The full changeover is required, not optional: a tool that only warns, or that keeps implicit behaviour as the default past the next major version, does not conform.
A tool MAY keep the old behaviour behind an explicit, documented opt-out (for example `--legacy-implicit`) for one further major version, and the opt-out MUST itself warn on every use.

== CLI styles

[NOTE]
====
This note is non-normative.

CLI _styles_ will each have their own behaviour contract.
The *strict style* is the default and is the style this page defines.

A future *natural-language style* (for example a universal `install <thing>` that resolves a name across package managers and prints disambiguation output) may allow implicit resolution under its own contract.
That contract will require the tool to show what it resolved, offer disambiguation, and never act on an ambiguous match without confirmation.

The natural-language style is to be specified separately (TBD; no page yet).
Until it is, no tool can claim it, and every conforming tool is held to the strict style.
====

== Examples

=== Unknown command

Non-conforming: the tool treats the typo as a target and acts on it.

[source,text]
----
$ pkg isntall webapp
Fetching package 'isntall'...
error: package 'isntall' not found in registry
$ echo $?
1
----

Conforming:

[source,text]
----
$ pkg isntall webapp
error: unknown command 'isntall'
  did you mean: install
  valid commands: install, remove, update, list, run, help
  see: pkg help
$ echo $?
2
----

=== A no-argument tool given an argument

Non-conforming: the argument is silently ignored, and the user cannot tell whether it did anything.

[source,text]
----
$ settings-gui --reset
(window opens; nothing is reset)
----

Conforming:

[source,text]
----
$ settings-gui --reset
error: settings-gui takes no arguments or flags; received '--reset'
  see: settings-gui --help
$ echo $?
2
----

=== Worked migration: dub and redub

`dub` treats an unknown first word as a package to fetch and run, and `redub` is a drop-in replacement for part of `dub`.

*Wrapper: `dub search` under redub.*
Non-conforming, the replacement guesses or silently does nothing useful:

[source,text]
----
$ redub search json
(builds the current project, or exits 0 with no output)
----

Conforming (CD-10):

[source,text]
----
$ redub search json
error: redub does not implement 'search'
  'search' is implemented by dub: dub search json
  see: redub help for the commands redub implements
$ echo $?
2
----

*Implicit catch-all: `dub foo` running a package.*
Today (non-conforming):

[source,text]
----
$ dub foo
Fetching foo 1.2.0...
Building foo ~master...
Running foo
----

Current major version, migration release (CD-11): behaviour unchanged, warning on every use, strict opt-in available.

[source,text]
----
$ dub foo
warning: 'foo' is not a dub command; running package 'foo' implicitly is deprecated
  use: dub run foo
  this will be an error in the next major version; enable now with --strict or DUB_STRICT=1
Fetching foo 1.2.0...
----

[source,text]
----
$ dub --strict foo
error: unknown command 'foo'
  to run a package named foo: dub run foo
  see: dub help
$ echo $?
2
----

Next major version (CD-12): the strict error above is the default for `dub foo`; `dub run foo` is the only way to run the package.

== Conformance checklist

* [ ] An unknown command prints `unknown command <X>`, a did-you-mean suggestion when one is close, and the valid commands or the help command (CD-1).
* [ ] Unknown commands go to stderr and exit `2`, and nothing is fetched, written, built or run first (CD-1, CD-2).
* [ ] No bare word is ever treated as a package, file or target; running one needs an explicit command such as `run <pkg>` (CD-3, CD-4).
* [ ] A bare invocation shows help, or runs a documented default and says which action it ran (CD-5, CD-6).
* [ ] A tool or GUI launcher that takes no arguments errors on any argument or flag it receives (CD-7).
* [ ] Unknown flags, extra positionals and missing arguments are usage errors with exit `2` (CD-8).
* [ ] A wrapper or drop-in replacement forwards only commands the underlying tool implements, and names the tool that implements anything else (CD-9, CD-10).
* [ ] A tool with implicit behaviour warns on every implicit use with the explicit replacement, and offers a strict opt-in (CD-11).
* [ ] Strict errors are the default by the next major version; warnings alone do not conform (CD-12).

== Rationale

* *Guessing turns typos into actions.* A catch-all that fetches or runs whatever word it is given converts a misspelling into a network fetch, a build, or arbitrary code execution. An error costs one retry; a wrong guess can cost much more.
* *Silence hides surface.* When a tool ignores input it does not understand, users and agents cannot tell whether a flag did something, did nothing, or does something undocumented. Rejecting it proves there is no hidden surface.
* *Agents read errors, not intent.* An agent that typos a command needs an exit code and a suggestion it can act on, not a run of an unrelated package.
* *Wrappers must not pretend.* A drop-in replacement that guesses at commands it does not implement breaks scripts in ways that look like success. Naming the tool that does implement the command keeps the user moving.
* *Warnings alone never finish a migration.* Deprecation warnings that never become errors leave implicit behaviour in place forever. A dated changeover at the next major version is what actually removes it.

See also xref:standard-cli-output.adoc[CLI Output] for where errors are printed and what exit codes mean.
